# Rust 自研引擎 vs foliate-js 重写可行性评估

> 状态：**评估文档（决策参考）**。本文只回答一个问题：**要不要为了「大章节卡顿」把渲染内核从 foliate-js 整体重写成 Rust+Kotlin**，以及如果要做、以什么代价、风险在哪。
> 相关背景：大章节根因见 [`ARCHITECTURE.md`](ARCHITECTURE.md) §8，屏级小节实施计划见 [`PAGINATION_SPLIT_PLAN.md`](PAGINATION_SPLIT_PLAN.md)。
> 编写日期：2026-08-23。

---

## 1. 触发背景与目标

当前痛点（真实且已定位）：技术类书籍（GIMP 3.0 手册「章节长、样式复杂」）在大章节里**打开、翻到、翻页、改设置重排全面卡顿**。根因在 §8.1 已由源码确认：

> 整章 = 一个 section = 一个 View，CSS columns 一次性碎片化整章 → 单 chrome DOM/scrollWidth/layout 全按整章量存在 → 内存与 CPU 随章长增长。

评估目标：**哪个方案能耗最少地达成「大章节顺滑 + 基点稳定 + 复杂排版（MathML/SVG/表格）不退化 + 可维护」**。

---

## 2. 两案对比总览

| 维度 | A. foliate-js（屏级小节切分） | B. Rust 自研引擎 |
|---|---|---|
| 核心难点 | 离屏量断点 + 切片（见 SplitPlan） | 分页/断行/避头尾/孤行/索引，**并**自研整套底层 |
| 排版/断行/字形/公式 | 浏览器免费提供（成熟） | 全部自己接 ✓/写 |
| 大章卡顿定位 | 直接打根因（§8.3） | 重新实现一个能分页的引擎才能打根因 |
| 改动范围 | 在现有工程上追加 6 步 | 推翻现有渲染层，重写引擎 |
| 技术风险 | 断点测量的稳定性 | stylo/parley 集成 + 复杂排版长尾 |
| 可维护性 | 复用浏览器演进 | 自持构建链 + 每个 crate 的演进 |
| 首版可达性 | Step1+2 POC 可快速验证 | 数千行起步，首版仍缺选区/笔记 |

---

## 3. 关键判断：两条路的难点是同一个，Rust 更贵

「大章分页 + 字符偏移锚点」这个**核心难题两边都要写**（切分方案要量断点、Rust 方案要写分页器），谁也躲不掉。差别只在于其余大部分：

- **A 路线**：浏览器已 battle-tested 的分页/断行/字形/基线对齐/公式排版全免费，你只写「量断点 + 切片」。
- **B 路线**：除了同样解决分页，还要啃下 **CSS 层叠、断行、避头尾、内联公式基线、选区、字体回退** 的全部边界 case——浏览器免费给你的东西你全部亲手重做，质量大概率仍**低于**浏览器。

**结论：B 是严格更贵、同样或更差的选择**，除非 A 被证明是死路。

## 4. Rust 方案的真实成本（手写量估计被低估处）

Rust 方案的 `2500–4000 行自写` 只算了**业务逻辑**，把核心依赖当成「拿来即用」。实际成本远高于此：

### 4.1 stylo：不是嵌入式库，是要你驱动的一台引擎（最大风险）

- stylo = Firefox/Servo 的样式系统，脱离 Gecko 需要你自备修道院：**节点驱动（match/层叠/继承/media query）、`Stylist`、事件循环**。
- **接 stylo 的胶水代码本身就是数千行**，且这是全案最硬、最影响「真机能否稳定渲染复杂 CSS」的集成点。
- 现实参照：Bogdan 的 `folio`（纯 Rust + Servo style 的阅读器）就是这个思路，**最终也没做到任意 EPUB 的生产级质量**。这是可复现的可行性证明，也是"长尾质量"的警钟。

### 4.2 parley：API 不稳，非成熟稳定件

- parley 正在快速迭代（Iced 配套，尚未稳定），字体回退/BIDI 依赖它 + harfbuzz。
- Android 交叉编译出干净 `cdylib` 本身是工程坑（Rust 交叉目标 + NDK 链），不是一行依赖的事。

### 4.3 技术书恰好在最该精的地方妥协

- B 方案把 **表格 / MathML / SVG 降级成位图**。而技术类 EPUB 是这些元素的重灾区。
- 高 DPI：这台平板 1840×2800（devicePixelRatio≈2.75）位图需按倍率渲染，**内存约翻 2.75²≈7.5 倍**。
- **表格/公式里文字丢失选中语义**——与项目已定的「标注/笔记」「科技渲染不退化」直接冲突。

### 4.4 与现有资产冲突

- 项目已投入：Kotlin `EpubParser`、`Location`/`ProgressConverter`、`FontParser`、Room 持久化、QuickJS 科技渲染方案（§7）、屏级切分方案（§8）全部对齐「**不自写分页内核**」。
- B 方案要么让 Kotlin 解析与 Rust 自解析**重复造两套**，要么作废现有数据层重移植。

## 5. 真实风险矩阵（对比）

| 风险项 | A. foliate 切分 | B. Rust 引擎 |
|---|---|---|
| 大章性能根治 | 只渲染 3 节，与章长解耦 ✓ | 需先写成可分页引擎才谈得上 |
| 复杂排版（公式/表格/SVG） | 保留（浏览器断行） | **降级位图，DPI+选中退化** |
| 选区 / 笔记 / 标注 | 保留浏览器原生 | MVP 只做书签，笔记后置 |
| 复杂度可控性 | 单一高风险点（断点） | **多个高风险点**（stylo 集成、断行、避头尾、孤行、公式基线） |
| 构建链 / 维护 | 现有 Gradle+WebView | `cdylib` 交叉编译 + 每 crate 演进随迁 |
| 首版验收速度 | Step1+2 POC 数步可见 | 数千行才见第一页 |

## 6. 结论与建议

### 结论
- **不建议现在整体重写 Rust**。它把一段「未知是否能根治大章卡顿」的旅程，垫上了「stylo/parley 集成 + 复杂排版长尾」这个更大、更难证伪的风险。
- 唯一能合理化 B 方案的前提是：**A 路线（屏级切分）被证明不可行**。但这个可行性目前尚未验证，不能先验地判它死刑。

### 建议（降低切分复杂度，非抛弃）
原方案纠结「运行时切分难、效果差」。可把切分的复杂从**运行时**挪到**一次性**：

1. 先做 [PAGINATION_SPLIT_PLAN.md](PAGINATION_SPLIT_PLAN.md) Step1+2 的 **POC**：离屏量断点 + 切片，用 GIMP 手册大章验证断点稳定。**通过→继续 A；不通过→才有理由启动 B。**
2. 若不想运行时重排：改为**导入/开书时一次性预处理**，把大章切成「屏级小节」小 HTML **落盘缓存**，设置变更只在**当前章**重切 → 摊薄「打开卡、改设置基点漂移」的复杂度。
3. Rust 若仍要做，应作为 **分阶段研究（spike）**而非全量投入：先写 TextFlow→分页核心（不碰 stylo），在硬编码章节上验证「字形测量 + 断行 + 避头尾」能达标，**再**评估是否值得接 stylo 上全量。切勿一步梭哈。

### 一句话
> 先用最省的方式**证伪或证实 foliate 断点**；证实即留 foliate，证伪再谈 Rust。直接梭哈 Rust = 在没验证最硬单点前烧光全部预算。

## 7. 附：如果要启动 Rust 研究，最小可证伪的验收项

（若采纳建议第 3 条，给它明确验收判据，避免无限期研究）

- [ ] **D1 字形+断行**：在硬编码章节（不做 EPUB/DOM/CSS），用 parley + harfbuzz 排出 CJK+西文混合段落，避头尾正确处理中文标点。
- [ ] **D2 分页+锚点**：块流式布局 + 单栏分页，改字号后按字符偏移锚回原段，基点不漂。
- [ ] **D3 stylo 可行性**：能对真实 EPUB 章节做 style cascade，输出节点计算样式；验证在 Android 真机交叉编译可用。
- [ ] **D4 公式/表格**：行内公式基线对齐 + 表格按 DPI 位图渲染的内存/清晰度，对比浏览器原生。

D1–D2 任一不过 → 停止 B；D3–D4 任一不过 → 只能降级复杂排版或继续用 A。这三条是是否值得梭哈的**红灯判据**。
